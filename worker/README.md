# fr255-prayers

Cloudflare Worker that serves the official Moroccan prayer times (Ministry of Habous) to a Garmin watch face.

## API

`GET /prayers?lat=33.57&lon=-7.59[&date=YYYY-MM-DD]`

```json
{"city":58,"date":"2026-11-11","today":[328,415,740,910,1055,1131],"tomorrow":[328,416,740,909,1054,1131]}
```

- The six numbers are minutes after midnight UTC: Fajr, sunrise, Dhuhr, Asr, Maghrib, Isha.
- `date` defaults to today in UTC. `tomorrow` is absent when the next row does not exist.
- Errors: `400` bad lat, lon or date; `404` unknown path, or no listed city within 25 km (`{"error":"no city near"}`, the watch then computes the times itself); `405` method other than GET; `502` Habous data unavailable or unreadable. Body: `{"error":"..."}`.

Data comes from `https://www.habous.gov.ma/data/horaires-YYYY-MM.js`, cached 32 days with the Workers Cache API. Habous publishes a month one time, thus the Worker gets each month file one time.
To keep the number of calls to Habous low, the Worker also caches the bad answers:

- A `404` from Habous (the month is not published) is kept 1 hour. In that hour the Worker does not call Habous for that month.
- A failure (other status, network error, or a body that does not parse) is kept 10 minutes. In those 10 minutes the Worker does not call Habous for that month.
- A second copy of each good month file is kept 62 days. The Worker serves it when Habous fails, thus `502` occurs only when no copy exists.

The cache is local to each Cloudflare location, and Cloudflare can remove an entry early.
The city is the nearest one in `data/cities.json` (haversine distance), at most 25 km away (`MAX_CITY_DISTANCE_KM`).

## Limits and abuse protection

- Rate limit: 20 requests per 60 seconds per client, keyed on the `CF-Connecting-IP` header (`unknown` when absent). It applies to every request, before routing, through the Workers Rate Limiting binding `PRAYERS_RATE_LIMITER`. Over the limit: `429`, header `Retry-After: 60`, body `{"error":"too many requests"}`.
- The binding is the native Cloudflare rate limiter. The `[[ratelimits]]` block in `wrangler.toml` defines it, and `wrangler deploy` creates it. Cloudflare counts per location and updates the counters with a small delay, so the limit is approximate: a short burst can pass more than 20 requests. In a test on the live Worker, a burst of 80 requests got 16 answers with `429`.
- If the binding is missing or fails (a test, or a run without it), the request is allowed: the limit is then off.
- Only `lat`, `lon` and `date` are accepted. Another name gives `400 {"error":"unknown parameter"}`, a repeated name gives `400 {"error":"duplicate parameter"}`.
- `lat` and `lon` must be decimals: optional minus, 1 to 3 digits, then optionally a dot and 1 to 6 digits (no exponent, hex, space or plus sign), within range.
- A URL longer than 200 characters gives `414 {"error":"uri too long"}`.

## Develop

```sh
npm install
npx vitest run test/<file>.test.ts   # run one test file at a time
npx tsc --noEmit
npx wrangler dev --port 8787
```

## Deploy

The GitHub workflow deploys the Worker after a push to `main` that changes this folder, when the tests pass. See the section "CI" in the README of the repository. For an urgent correction from a computer: `npx wrangler deploy`.

## City coordinates

`data/cities.json` is generated by `scripts/build-cities.py` (Python 3, standard library only).
Cities without a reliable match are listed in `data/UNMATCHED.md`. They have no coordinates and the Worker never returns them.

```sh
python3 -I scripts/build-cities.py test/fixtures/horaires-2026-11.js <dir>/MA.txt data/cities.json data/UNMATCHED.md
```
